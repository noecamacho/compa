# Hackathon requirements (Codex Build Day Guadalajara)

The rules COMPA must satisfy to be an eligible entry. Source: the event deck, cited as `s. N` ([sources/build-day-slides](sources/build-day-slides.md)). Everything here overrides the plan's own checklist where they differ.

## Deadlines (s. 1, s. 11, s. 13, s. 14)

| When (Guadalajara local time) | What |
| --- | --- |
| Wed 2026-10-28, 16:00–19:00 | Build Day: build and prepare the first demo |
| **Thu 2026-10-29, 10:00** | **New projects close; submit before this.** Voting opens |
| Fri 2026-10-30, 13:00 | Edits and voting close. The same project may be improved until then |
| Fri 2026-10-30, after 13:00 | Prizes |

The submission can be edited while submissions are open (submit page), so the first submission before Thursday 10:00 may be improved until Friday 13:00 (s. 11).

## What the submission must include (s. 9)

1. Project name and team members.
2. Problem it solves and proposed solution.
3. Repository link.
4. Demonstration video.
5. Live demo page.
6. Evidence of Codex use.

Submitted through the form linked from the deck (one submission per account, shared by the team).

## Eligibility (s. 10)

- Codex use with concrete evidence.
- Working demo and a README with instructions.
- New work for the event; no plagiarism, no pre-existing project presented as new.
- Reuse declared, with compatible licenses.
- Complete submission, on time, without secrets or private data.

The organizers check these before confirming winners (s. 10).

## Demo and README expectations (s. 7)

- Demo: one main journey that works end to end; test data and a result that can be verified.
- README: what the project does and how to run it; what was built during the Build Day and what is missing.

## Evidence of Codex use (s. 8, s. 14)

- A screenshot without sensitive data, or a short video segment.
- Show a concrete task done with Codex; explain where and how it was used; tell how the result was reviewed or tested.
- Hide keys, personal data and confidential information before publishing.

## Pre-submission checklist (s. 14)

- [ ] Main journey tested.
- [ ] README and every link reviewed.
- [ ] Codex evidence and "what was built here" included.
- [ ] Licenses, privacy and absence of secrets checked.
- [ ] Submitted before Thursday 29 at 10:00.

## Voting (s. 12)

One active vote per account, changeable while voting is open; votes decide winners among eligible projects; no fake accounts, bots or vote trading.

## Suggested working style (s. 2, s. 3, s. 5)

Build a first version someone can try; one person, one problem, one journey; leave secondary features for later. With Codex: explain goal, context and what must work; ask for a small plan before changes; work in reviewable steps; test the main journey and share errors; review before calling it done. This matches the plan's cut order ([mvp-scope](mvp-scope.md)) and work rules ([team-and-prs](team-and-prs.md)).

## Credits and access (s. 6)

Credits are handed out individually; follow the organizers' instructions; never share codes or private access information.

## Impact on COMPA

- The plan's delivery checklist ([delivery-checklist](delivery-checklist.md)) already covers the demo flow, Vercel deploy, README, backup video, public repo with license and the submission form. The deck adds: team member names, the problem and solution statement, a **live demo page** link, and **evidence of Codex use** as separate items (s. 9).
- Eligibility requires evidence of **Codex** specifically (s. 10); the plan's "How we used Codex" README section (PDF p. 20) satisfies the narrative, but a screenshot or video segment of a concrete Codex task is also required (s. 8). See [open-questions](open-questions.md) #19.
- "Reuse declared with compatible licenses" (s. 10) means the repository needs a license and a note on reused code; see [open-questions](open-questions.md) #14.
- "Without secrets or private data" (s. 10, s. 14): no keys in the repo, seed data must be fictional, the `/live` privacy rules apply ([privacy-consent](privacy-consent.md)).
