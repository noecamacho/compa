## 1. Decisions

| # | Decision |
| --- | --- |
| A1 | Scanning someone's personal QR **checks the scanner in automatically** to that person's current event (after the screen notice), then creates the request. A visitor without an account goes LinkedIn sign-in → check-in → request in one flow. |
| A2 | A person's **current event** is the most recent event they checked in to whose window contains now. If none, scanning their QR shows "not at an event right now". |
| A3 | The addressee learns about a request **live in the app** (a card with Accept / Decline and the "we already knew each other" tick, plus a badge). No push notifications. |
| A4 | The requester sees a **simple "Request sent"** (with the optional "we already knew each other" tick). When accepted, their app shows **"Connected! +20"** (or +10) live and unlocks the addressee's connections-only fields. |
| A5 | The big screen shows the **network visualization and counters**. Clicking a person opens their card (public fields, event points, connection count, rank); clicking empty space opens the **leaderboard**. |
| A6 | `/live` is **public** to anyone with the link and only ever shows name, photo, public fields, points and connection kinds. |
| A7 | A person's connections list is **grouped by person** with the history of meetings per event; requests waiting for their answer sit on top. |
| A9 | **Summaries** use the routes in `docs/contracts/ai-summaries-api.md` (`POST /api/transcribe`, `POST /api/interactions/draft`, `POST /api/interactions/:id/approve`); only members of an **accepted** connection may draft; approval awards `SUMMARY_POINTS` (+25) to both and broadcasts `summary.approved` (topics only) to `/live`. |
| A10 | **Public event routes are code-gated** (data model M19). Everything public about an event lives under `/api/e/{code}`: door, live snapshot, live person card, leaderboard and check-in. A malformed, unknown or rotated code returns the same `404 event_not_found` ("Event not found."), so responses never hint whether an event exists; malformed codes never reach the database. The slug routes `/api/events/{slug}/…` are removed; slugs remain for admin routes only. `GET /api/me` returns `currentEvent: { code, name }` for checked-in attendees. The live Realtime channel is `event:<code>:live`. **Landing** (`/`): one promise and the message that you get in only by scanning your event's QR; no public sign-up or sign-in; a signed-in person with a current event sees one "Back to my event" button to `/home`. **Locale**: Spanish when the first preferred language is `es*` (server `Accept-Language`, client `navigator.languages`), English otherwise (`lib/i18n.ts`); landing and event-entry copy exist in both (`lib/copy/en.ts`). Pages: `/e/{code}` (door), `/e/{code}/join` (screen notice → check-in → `/home`), `/e/{code}/live` (projected dashboard). Responsive targets: 390 / 834 / 1440, plus 1920×1080 for `/live` (captain decision, 2026-10-29). |
| A10a | **Amended 2026-10-29 (captain):** the landing at `compa.lol` offers "Entrar con LinkedIn" to everyone (one button for sign-up and sign-in, then `/home`). Events stay exclusive: joining an event still requires its QR link `/e/<code>`. Signed-in visitors see "Volver a mi evento" or "Ir a mi cuenta". |
| A8 | The personal QR encodes `https://<domain>/u/<handle>`. `users.handle` is added to the data model (§2). [Assumption: needed so QR URLs stay short and stable; confirm.] |
| A11 | **Super-admin console and real-mode test harness** (captain decision, 2026-10-29; data model M20). Only `role = super_admin` reaches `/admin` and `/api/admin/*`; everyone else, signed in or not, gets the plain `404 not_found`, and per-request mock headers do not open admin routes outside a mock deployment. `GET /api/me` returns `role` and `isTest` (`isAdmin` stays, derived from the role). Admin entry points render only for super admins (`/me` row, desktop pill). The test-user routes also accept `x-compa-automation: <TEST_AUTOMATION_SECRET>` (constant-time compare, never logged; unset disables it). Sessions are minted only for `is_test` users. Method: `docs/testing/real-mode.md`. |

Add to `users` (see the data-model spec):


`interests` is seeded from `lib/topics.ts` (already on `main`) so the AI summary vocabulary and profile interests stay one list.

## 3. Conventions

- **Auth**: Supabase Auth session cookie (`@supabase/ssr`), LinkedIn OIDC or an email magic link via `POST /api/auth/email` (M2). `requireUser()` resolves the signed-in `users` row or returns 401.
- **Validation**: every request body and query is parsed with zod; failures return 400 with field errors.
- **Errors**: `{ "error": { "code": "snake_case", "message": "Plain sentence.", "fields"?: { … } } }`. 401 not signed in, 403 wrong actor, 404 not found or not visible to you, 409 state conflict, 400 invalid input, 429 `rate_limited` (with `Retry-After` in seconds) or `limit_reached` (a per-event or per-connection cap, no retry) when a signed-in user passes a per-user limit (`lib/api/rate-limits.ts`, T-036).
- **IDs**: UUIDs. **Times**: ISO 8601 UTC.
- **Server only**: all database access uses the service-role key in route handlers; RLS denies clients (data-model §4.7).

## 4. Shared types

```ts
type Visibility = "public" | "connections" | "hidden";
type LinkKey = "linkedin" | "github" | "x" | "instagram" | "web";

type Card = {                       // another person, as YOU may see them (§6)
  id: string; handle: string; name: string; photoUrl: string | null;
  headline?: string; company?: string; interests?: string[];
  links?: Partial<Record<LinkKey, string>>;
};

type Me = Card & {
  email: string | null;
  visibility: { headline: Visibility; company: Visibility; interests: Visibility; links: Record<LinkKey, Visibility> };
  nameEdited: boolean; photoEdited: boolean; isAdmin: boolean;
  currentEvent: { code: string; name: string } | null; // A10: the access code, checked-in attendees only
};

type ConnectionStatusForMe = "pending" | "accepted" | "expired" | "declined"; // "declined" only ever shown to the addressee (§7.4)
```

### 5.5 Admin console and test harness (A11)

Every route answers `404 not_found` to anyone but a super admin. Schemas: `lib/api/admin-schemas.ts`; contract: `openapi.json` (tags `admin`, `testing`).

| Route | Auth | Purpose |
| --- | --- | --- |

## 6. Visibility filter (one function, server only)

`toCard(owner, viewerId | null)`:

1. Always: `id`, `handle`, `name`, `photoUrl`.
2. For `headline`, `company`, `interests` and each link: include when the level is `public`; or when it is `connections` **and** `viewerId` has an **accepted** connection with `owner` at any event; never when `hidden`.
3. Never: `email`, `auth_user_id`, `linkedin_sub`, `linkedin_raw`, `is_admin`.
4. `viewerId = null` (the big screen) means public fields only.

Every response that describes another person goes through it. Hidden data is never sent to the client.

## 7. Behavior

### 7.1 Scan → request (`POST /api/connections`)

1. Resolve the target by `toHandle`; 404 if missing; 409 `self_connection` if it is the scanner.
2. Find the target's current event (A2); 409 `not_at_event` if none.
3. If the scanner is not checked in there: require `screenConsent: true` (else 409 `consent_required`, which makes the client show the screen notice and retry), then insert the check-in.
4. Insert `connections (event_id, requester_id, addressee_id, requester_knew)`; on the per-event pair conflict, return the existing row with 200 (no new request, no message to the addressee).
5. Broadcast to the addressee (§8).

### 7.2 Accept

Inside one transaction, guarded by `where status = 'pending'`:

1. Event still running, else 409 `event_ended`.
2. Set `addressee_knew` from the body.
3. `kind = reconnection` if an accepted connection exists for the same pair at another event that started earlier, or either `knew` is true; else `new`. `points = 20 | 10` (M3, M4).
4. Update status, kind, points, `responded_at`.
5. Broadcast to the requester ("Connected! +N" with the now-unlocked `Card`) and to the event's live channel (§8).

### 7.3 Expiry

A `pending` row whose event has ended is reported as `expired` (evaluated on read). Accept and decline on it return 409 `event_ended`.

### 7.4 Silent decline

The addressee sees `declined`. The requester sees `pending` while the event runs and `expired` after it ends. Nothing is broadcast on decline. The pair cannot connect again at that event (unique index; open question #23 tracks reverse scans).

### 7.5 Connections list

- `incoming`: requests where I am the addressee, `pending`, event running; newest first.
- `people`: one entry per other person with any connection involving me, meetings newest first; `totals` sum my accepted points.
- My sent requests appear as meetings with status `pending` / `expired` (never `declined`, §7.4).

## 8. Realtime

| Channel | Who subscribes | Message | Payload |
| --- | --- | --- | --- |
| `user:<userId>` (private) | that user's phone | `request.received` | `{ connectionId, from: Card (public view), event: { slug, name } }` |
| `user:<userId>` (private) | that user's phone | `request.accepted` | `{ connectionId, kind, points, to: Card (unlocked view) }` |
| `user:<userId>` (private) | that user's phone | `invitee.connected` | `{ invitee: Card }` |
| `user:<userId>` (private) | that user's phone | `badge.earned` | `{ badgeId, badgeName }` |
| `user:<userId>` (private) | that user's other tabs | `notifications.seen` | `{ seenThrough }` |
| `event:<code>:live` (public, A10) | `/live` | `connection.accepted` | `{ id, a: { id, name, photoUrl }, b: { … }, kind, at }` |
| `event:<code>:live` (public, A10) | `/live` | `attendee.checked_in` | `{ id, name, photoUrl }` |

- The server sends these as Supabase Realtime **Broadcast** messages after each write.
- Private `user:` channels use Realtime Authorization: migration `0011_realtime_user_channels` adds a `SELECT` policy on `realtime.messages` so an `authenticated` user joins only `user:<own users.id>` (resolved from `auth.uid()` by the security definer function `compa_own_user_topic()`). The client treats every message as a poke and refetches `GET /api/notifications`, so a lost message costs nothing; it polls every 3 s while the channel is down and every 30 s while it is up (T-080, T-081).
- **Web Push** (T-080): the same four person events (request, accepted, invitee connected, badge earned) also go to every browser the person turned alerts on in, after the response (`after()`). `POST /api/push/subscriptions` and `DELETE /api/push/subscriptions` store the browser's subscription; endpoints must be a browser push service over https (SSRF guard), at most 10 per person, 404/410 from the push service deletes it. VAPID keys come from `NEXT_PUBLIC_VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` and `VAPID_SUBJECT`; unset means push is off. The pushed text uses the language stored with the subscription.
- Payloads carry only ids, names, photos, kinds and points. Never email, never anything about a decline.
